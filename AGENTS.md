# Beelicious engineering guide

## Architecture and boundaries

Use a TypeScript modular monolith with npm workspaces. `apps/api` owns HTTP, configuration, logging, and process lifecycle. `packages/database` owns Prisma configuration, migrations, and connections. `packages/shared` contains only reusable types and pure utilities. Dependencies flow from the API to packages; packages must not import the API. Expose packages through their public exports, never through cross-workspace source paths.

Phase 3 adds tenant/catalog/customer services and read-only catalog HTTP endpoints alongside the existing messaging integrations. Warung Babe has only the explicitly supplied development prototype seed. Do not add conversation state machines, carts, orders, pickup scheduling, payments, authentication, dashboards, AI, production phone registration, or deployment without an explicit subsequent-phase request.

## Conventions

Use strict TypeScript, ESM, NodeNext resolution, and `.js` extensions in relative TypeScript imports. Keep handwritten sources in `src`, compiled files in `dist`, and tests outside `src`. Prefer small functions and explicit dependencies over abstraction layers. Do not add microservices, Redis, orchestration frameworks, or agents.

Construct Fastify without opening a socket. Only entrypoints (server and local CLIs) read process configuration; only the server installs signal handlers. Each application owns its database instance and disconnects it on close. Liveness is independent of PostgreSQL; readiness executes a real query and must recover after an outage.

## Database

Use Prisma 7 configuration and the PostgreSQL driver adapter. Keep Prisma CLI, client, and adapter versions aligned. Generate with `prisma generate`. The Phase 1 baseline remains unchanged; Phase 2 adds the WhatsAppEvent infrastructure inbox and Phase 3 adds a separate additive catalog/customer migration. Do not edit generated code or applied migration SQL. Add new migrations for schema changes. `db:migrate` applies checked-in migrations; `db:migrate:dev` authors migrations against a development database. Never reset a database or remove its volume without explicit authorization.

## Security

Never commit `.env`, credentials, tokens, connection URLs with passwords, or generated artifacts. `.env.example` contains placeholders only. Validate configuration before allocating resources; report invalid field names without values. Do not log environment objects, raw database exceptions, authorization headers, or cookies. Do not expose database error details over HTTP. Bind local PostgreSQL to loopback. Preserve existing files and local tool settings.

## Verification

Use `npm ci`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, and `npm run build`. With local PostgreSQL running, also run `npm run db:migrate` and `npm run test:integration`. Verify the compiled server, outage recovery, and graceful shutdown for lifecycle changes. Unit tests must not require PostgreSQL; integration tests must fail visibly when their required service is unavailable. Report only checks actually run, and distinguish skipped checks from passes.

## WhatsApp integration

Keep Meta payloads in `apps/api/src/modules/whatsapp`; future conversation code must use normalized inputs. Never add an unauthenticated send endpoint. Use native fetch, explicit configured Graph version, five-second HTTP deadlines, and typed sanitized failures. The documented v26.0 target requires live account verification; never claim a mock proves Meta delivery.

WhatsApp defaults off. Require all Meta settings when enabled. The greeting bot requires development mode, explicit enablement, and approved recipients, checked again before sending. Preserve account scope, timestamp eligibility, and message/status separation. Store minimal normalized data and greeting classification rather than raw payloads or arbitrary text.

Authenticate raw Buffer bytes with HMAC-SHA256 and timing-safe comparison before JSON parsing. Keep the raw parser encapsulated to webhook routes. Strip query strings from request logs so GET verification tokens cannot leak. Persist relevant batches atomically before HTTP 200; use 503 for storage failure. Unsupported signed events can be acknowledged without work.

PostgreSQL uniqueness owns deduplication. The worker owns retries and uses atomic claims, ownership tokens, and leases. Commit `sending` before HTTP. Reclaim expired pre-send work; never automatically resend interrupted/ambiguous sends. Explicit Meta rate-limit rejections are the only automatic HTTP retry category, up to three total attempts. Preserve `uncertain` records for deliberate investigation; do not reset them or purge deduplication keys casually. Keep worker shutdown ahead of database disconnect. Start workers only when listening, not during app construction/injection.

WhatsApp integration tests use a separate migrated database ending in `_test`, derived from DATABASE_URL unless WHATSAPP_TEST_DATABASE_URL overrides it. Run `npm run db:migrate:test` after creating that database. Never truncate or reset development inbox data. Mock every Meta request in tests, including database-connected tests. Test concurrency, restart recovery, expired leases, ambiguous send suppression, retry scheduling, and logging privacy. Safe inspection is available through `npm run whatsapp:events`; the development-only `whatsapp:send` CLI sends the fixed greeting to the first approved test recipient and is a deliberate live action.

## Phase 2B messaging providers

`MESSAGING_PROVIDER` selects `cloud-api` (backward-compatible default), `baileys`, or `mock`; `WHATSAPP_ENABLED` remains the default-off master switch. Initialize only the selected provider and require credentials only for it. Preserve the official Meta client, signed webhook routes, Graph settings, existing deduplication hashes, and retry behavior. Phase 3 authorizes catalog/customer work only; keep all later-phase exclusions in force.

Provider-independent contracts, greeting classification, and the shared durable worker live in `apps/api/src/modules/messaging`. Keep Meta payloads in `modules/whatsapp` and Baileys objects in `messaging/providers/baileys`. Normalize provider/account/message/chat/sender IDs, text, timestamps, type, and direction before business logic. Persist only minimal routing/eligibility metadata and greeting classification, never arbitrary incoming text or raw payloads. Use the existing WhatsAppEvent inbox; no Phase 2B schema migration is required.

Claims and expired-send recovery require provider/account scope, including compatibility for legacy Cloud rows. Never claim or discard another provider's pending work after a configuration switch. PostgreSQL uniqueness remains the deduplication authority. Keep `sending` committed before transport invocation, leases and ownership checks intact, and ambiguous sends uncertain. Only explicit Meta rate-limit rejection has automatic sending retries. Never automatically retry a Baileys send after invocation, including timeout/disconnect. Mock every WhatsApp transport in tests.

Baileys is unofficial, temporary, development-only, and carries account-restriction risk. Use the pinned maintained `@whiskeysockets/baileys` version and consult its installed API declarations/versioned upstream sources before upgrades. No platform evasion, bulk messaging, production support, or unsolicited conversations. Greetings require development mode, explicit bot enablement, and `BAILEYS_ALLOWED_TEST_CONTACTS`, rechecked before sending. Preserve PN/LID routing addresses; approve opaque LIDs only through trusted alternate phone identifiers or Baileys mappings. Unknown identities receive no reply.

Accept only fresh one-to-one incoming original text in notify batches. Ignore self/outgoing messages, groups, broadcasts, newsletters, history/append/placeholder events, media, captions, wrappers, and protocol edits. Enforce the process-start timestamp cutoff with five seconds of skew; committed inbox work retains the 24-hour expiry. Process every eligible message in a batch. Keep delivery updates separate from commands.

Start sockets/workers only on listening, never app construction/injection. Maintain one socket generation/listener set and one bounded reconnect timer. Logout/bad sessions/replaced connections stop reconnecting; never auto-delete authentication. Stop ingress and worker activity before socket/auth cleanup and database disconnect. Halt Baileys ingestion on storage failure; document that replay before database commit is not guaranteed.

Local `useMultiFileAuthState` is permitted only for development. Use the ignored `.local/baileys-auth` default or private storage outside the checkout; never point it at application sources. Validate existing auth before the helper can silently regenerate corrupt credentials. Serialize credential/key writes, use private permissions, and hold the auth-directory lock. The atomic heartbeat lock may need 60 seconds for stale recovery after a crash; never remove a live lock. This is single-host storage, not a production session backend. Auth data is unencrypted and file writes are not crash-atomic. Never log raw library errors, payloads, phone numbers, JIDs, message content, or pairing material. Render QR only to an interactive local terminal, never an HTTP endpoint or structured logs.

Mock records outgoing messages in memory and accepts explicit test injection without public HTTP endpoints. The existing `whatsapp:send` remains a deliberate Cloud-only live CLI; `whatsapp:events` stays safe for all inbox providers. Keep real-device pairing/reception/delivery/restart restoration explicitly unverified until demonstrated; mocks never establish live connectivity.

## Phase 3 domain and catalog

TenantService, MenuCategoryService, MenuService, and CustomerService live in API domain modules. Use the existing application-owned Prisma client through `@beelicious/database` public exports; do not create service-specific pools or import generated workspace source paths. Customer registration remains service-only: do not change the greeting pipeline or register arbitrary inbound contacts. Keep the ignored active development configuration on Baileys and preserve both real adapters and mock.

Models: Tenant -> MenuCategory -> MenuItem; MenuItem also references Tenant. Customer -> CustomerMessagingIdentity is independent of catalog tenants. Use UUID internal IDs and timestamps. Tenant slugs are unique. Every category/item operation requires tenant context. A composite `(tenantId, categoryId)` foreign key enforces category ownership; preserve it in future migrations. Prices are integer Rupiah, validated between zero and PostgreSQL Int maximum; preserve the database nonnegative CHECK. Deterministic category/item order is sortOrder then ID. All foreign-key update/delete rules are restrictive; normal operations deactivate rather than delete. No deletion services or cascade deletion are provided.

Validate service inputs with strict Zod schemas and convert raw persistence failures into sanitized DomainError codes. Never expose raw Prisma errors or values in logs/responses. Public catalog routes use explicit DTO/response schemas and `{ data }` / `{ error: { code, message } }` envelopes. Require active tenants, active categories, and available items; hidden/cross-tenant resources return 404. Do not expose administrative writes or customers until explicitly authorized authentication work exists. Catalog lists are currently unpaginated.

Customer identities are unique by provider/accountId/providerUserId. Use existing normalized accountId and senderId, preserving JIDs/LIDs and provider namespaces; never infer a phone number from an opaque LID or merge by phone equality. Register customer+identity atomically and recover concurrent uniqueness races without orphan customers. Additional identity association requires a trusted caller's independent ownership verification for the exact customer and identity; `verified: true` is an internal contract, not proof or an authentication boundary. This phase implements no verification workflow or inbound association. Never transfer an identity to another customer. PhoneNumber is nullable/reserved and is not populated by current services. Keep PII out of public responses and logs.

`npm run db:seed` explicitly invokes the development-only CLI via Prisma 7 migrations.seed configuration. It creates only Warung Babe, Makanan/Minuman, and the supplied Nasi Goreng Spesial Rp20,000 / Es Teh Manis Rp5,000 prototype examples. Preserve fixed fixture UUIDs, transactional rollback, the seed transaction advisory lock, and existing edits. Reserved-ID/slug ownership conflicts must fail safely. Never seed automatically at startup or run against production. Applied migration SQL must not be edited; future integrity changes need new migrations.

Run `npm run db:migrate:test` before database integration tests. Domain tests use the same guarded separate `_test` database as messaging tests and remove only suite-owned rows in dependency order. Never truncate/reset or seed the development inbox. Test direct invalid database writes, tenant isolation, concurrent registration/association/seeding, identity namespace separation, public visibility and privacy, and messaging regressions. User-confirmed pre-Phase-3 Baileys pairing/greeting success is distinct from a post-change live test; mocks do not verify delivery or restart restoration. Phase 4 may consume these services but is not authorized by Phase 3.

## Phase 4 conversation engine

Phase 4 authorizes deterministic persisted catalog browsing and approved-contact customer registration. It supersedes earlier prohibitions on conversation states/inbound registration only for this scope. Keep all cart, quantity, ordering, pickup, payment, dashboard, authentication, AI, and deployment exclusions. Preserve Baileys, Cloud API, mock, existing allowlists, signed webhook handling, account scope, and transport retry policy.

`CONVERSATION_ENABLED` defaults false and requires development mode, WHATSAPP_ENABLED, WHATSAPP_TEST_BOT_ENABLED, and the selected provider's approved recipients. New messages use the engine only when enabled; otherwise preserve the fixed greeting. Keep the local active provider Baileys. Legacy greeting records retain their handler; disabled conversation records stay pending. Never enable live messaging as an automated verification step.

The API conversation module parses only start/back/cancel/help/numeric/invalid/empty command classes. Persist no arbitrary incoming text. Typed states are IDLE, SELECT_TENANT, SELECT_CATEGORY, SELECT_MENU, VIEW_MENU_ITEM. Use existing transaction-compatible catalog/customer services through database public exports. List five options per screen; 1–5 select, 8/9 paginate, 0/Kembali go back. Menu/Halo/Hi/Mulai restart; Batal clears context; Bantuan preserves selections and does not extend inactivity. Sessions expire after 30 minutes. Store/revalidate option ID mappings and revision fingerprints; catalog changes refresh instead of reinterpreting a number. Recheck active tenant/category and item availability; recover to a valid parent. Do not expose IDs or ordering actions in messages.

ConversationSession is unique per messaging identity, whose provider/account/user namespace defines isolation; do not merge PN/LID/provider identities. Restrictive composite foreign keys and the session context CHECK enforce ownership/state shape. ConversationTurn uniquely references one inbox event and session revision, storing one prepared response. Keep the application-owned pool and commit transition plus response atomically under event/session row locks before entering sending. Do not put network calls inside a database transaction. Validate lease ownership and bind input to its stored event before registration/preparation.

Inbox stream hashes and receipt sequences provide per-identity database receipt order. Acquire sorted advisory stream locks when inserting batches; never claim later stream work ahead of pending/processing/sending predecessors. Reuse a prepared turn after recovery instead of applying input twice. Preparation failure claims are bounded to five; raw exceptions never reach logs. PostgreSQL outages must not cause uncommitted replies. Only explicit Meta rate-limit rejection retries sends; interrupted/ambiguous sending remains uncertain. Atomically mark refresh-required when a prepared send is failed/ignored/uncertain or its sending lease expires. Help must preserve that flag; the next non-global command refreshes instead of selecting.

Use separate guarded test databases, mocked transports, and suite-owned cleanup: turns, sessions, identities, customers, inbox events, then owned catalog rows. Never purge production/development dedup keys or sessions casually. Add migrations instead of editing applied SQL. Test competing workers, sequence blocking during retries, prepare/send crash boundaries, stale lease tokens, provider/account/JID/LID separation, catalog changes, expiry, refresh recovery, flag-off greeting compatibility, and application restarts. Live Phase 4 Baileys delivery/restoration is unverified until a real device demonstrates it. Phase 5 may extend the engine but is not authorized here.

## Phase 5 shopping carts

Phase 5 explicitly authorizes quantity selection and persistent carts, superseding earlier cart/quantity prohibitions only for this scope. Keep all order, checkout, pickup, payment, authentication, dashboard, AI, deployment, and new-provider exclusions. Preserve Baileys as the local active provider, Cloud API and mock, flags, allowlists, and messaging transport behavior. Never enable messaging or send live messages as automated verification.

CartService and pure pricing live in `apps/api/src/modules/cart`. Cart belongs to a customer, identity, conversation session, and tenant. A PostgreSQL partial unique index allows one ACTIVE or READY cart per session; ABANDONED carts are historical. Composite restrictive FKs bind customer/identity/session and menu/cart tenant ownership. CartItem is unique by cart/menu, has positive quantity and nonnegative integer Rupiah saved unitPrice. Preserve the partial index, CHECKs, composite FKs, and all prior integrity constraints in future migrations. Never edit the applied `cart_states`/`carts` migrations; enum additions are committed separately before CHECK usage.

Carts are per conversation identity/account/provider, even for reliably linked identities. Internal customer/session scope must be validated before reads and writes. No unauthenticated cart endpoints are authorized. Repeated items increment one line; the configurable CART_MAX_ITEM_QUANTITY (default20, range1–1000) applies to the combined item quantity. Lowering the limit does not rewrite existing carts. CartService can bind to the engine-owned Prisma transaction; standalone operations own bounded-retry transactions. Lock session then cart, followed by deterministic catalog share locks. Recognize Prisma 7 ORM and raw-query serialization failures; propagate conflicts to the enclosing transaction retry boundary, never retry a partial mutation or transport call independently.

Commit cart mutation, session transition, and unique prepared ConversationTurn together. Look up an existing event turn before mutating. Preserve receipt ordering, provider scopes, leases, approval checks, sending-before-transport commit, uncertain-send suppression, and explicit Cloud rate-limit-only retries. After failed/ambiguous prepared delivery, refresh committed state before another selection. No exactly-once WhatsApp delivery claim is permitted.

Use saved unitPrice for summaries and pure safe-integer multiplication/summation; reject invalid amounts/overflow. Prices come from MenuService/database, never user input. Revalidate active tenant/category, availability, quantity, and current price before additions/updates/READY. Price changes require an explicit proposal acknowledgement bound to cart revision, catalog pricing, and the pending action. Apply accepted prices and action atomically; changed proposals require another acknowledgement. Removal/clear can resolve unavailable lines. READY is selections only, never an order/reservation/payment request.

Keep VIEW_MENU_ITEM and offer numeric entry to SELECT_QUANTITY. Extend typed states with CART_ACTION, CART_REVIEW, CART_EDIT_QUANTITY, CART_EDIT_QUANTITY_INPUT, CART_REMOVE_ITEM, CART_READY, and confirmation states for clear/switch/reopen/prices. Accept Phase 4 JSON with safe defaults; validate pending actions. Numeric0 is Back, not zero quantity. Cart summaries/edit lists paginate five lines (8/9), ordered createdAt then ID, with stable mappings/fingerprints and whole-cart subtotal. Keep text under4096 and navigation on separate lines with bold command labels, not middle-dot separators.

Global Keranjang retrieves the current cart. Menu/greetings, Batal, expiry, and restart preserve it. Batal clears browsing context only. READY edits require explicit reopen confirmation. Nonempty tenant switches require confirmation before marking the old cart ABANDONED; refusal preserves it. Empty carts may switch directly. Clear requires separate confirmation and retains a usable ACTIVE cart. No implicit cart deletion, automatic expiry, provider identity merging, or retention job is authorized.

Test direct invalid writes, cart/customer/session/tenant isolation, repeated and concurrent additions, max quantity, pricing acknowledgements, stale numeric/confirmation mappings, READY lifecycle, navigation, expiry/restarts, rollback, duplicate/recovered turns, ambiguous sends, and mocked real-adapter ingress. Use the separate migrated `_test` database and cleanup suite-owned CartItems/Carts before session/customer/catalog rows. Keep readiness fixtures independent of local flags. Run all existing checks and report only actual results. Live Phase 5 Baileys delivery/restoration is unverified until demonstrated with a real device. Phase 6 may consume READY carts with revalidation; do not implement it here.

## Phase 6 checkout, pickup, and Sandbox payments

Phase 6 authorizes checkout, orders, pickup reservations, image messaging, and mock/Midtrans Sandbox payments only. Earlier exclusions are superseded only for these capabilities. No production collection, payout, refund, dashboard, fulfillment workflow, or deployment is authorized. Preserve existing Baileys/Cloud/mock text paths, account scope, flags, allowlists, signed Meta webhooks, inbox receipt ordering, and uncertain-send suppression. Never enable messaging or initiate real external transactions as automated verification.

Checkout modules live in `apps/api/src/modules/checkout`; conversation integration is provider-neutral. CHECKOUT_ENABLED defaults false and requires development conversation configuration. PAYMENT_PROVIDER defaults mock; Midtrans requires SB- Server Key, merchant ID, and sandbox environment. Initialize only the active gateway. Do not require a Client Key. Configuration errors contain field names only. Keep the ignored active messaging configuration on Baileys.

TenantOperatingHour stores weekday (Sunday=0), local minutes after midnight, and IANA timezone. PickupSlot stores UTC timestamps, configured capacity, closure flag, and a trigger-maintained reservedCount. The development seed adds daily 07:00–18:00 Asia/Jakarta only, preserving edits. This is an unverified merchant assumption. Slots default to 30 minutes, five orders, 60-minute lead time, seven days. Reject DST gaps/folds; no overnight intervals. No existing slot's capacity or closure is overwritten by generation. An effective HELD or CONFIRMED reservation consumes one unit per order. Overdue uncertain holds still consume capacity. Preserve guarded counter triggers, CHECKs, and composite foreign keys in additive migrations; never edit applied SQL or write reservedCount directly.

OrderService binds to the engine transaction or owns bounded-retry RepeatableRead transactions. Lock session, cart/catalog, then slot. Checkout commits immutable order-item snapshots, source cart CHECKED_OUT, reservation HELD, and payment INITIATING with the prepared ConversationTurn. No gateway or messaging network request belongs inside that transaction. One source cart maps to one order; repeated confirmation returns it. One pending order per session is database-enforced; service locks also block new checkout while review is outstanding. Late historical settlement may create a review alongside an already-existing newer checkout; preserve both rather than losing received-payment evidence. Paid/terminal order records never reuse their source cart. Explicit retry copies available items to a fresh editable cart with saved prices so the existing acknowledgement flow handles price changes.

Payment has a unique provider/merchant/reference and one attempt per order. References, amounts, currency, and owner are immutable; success cannot regress. The fixed Sandbox API uses native fetch, Basic Server-Key authorization, five-second deadlines, supported custom_expiry, and configured HTTPS notification override if present. Commit creationStarted before invocation; never automatically invoke charge again after it might have run. Reconcile the original reference; a 404 after uncertain invocation is not proof of cancellation. Unknown/mismatched evidence goes to review, retains capacity, and preserves minimal audit evidence. Terminal failures are also reconciled during a 24-hour recovery window for missed late settlement. Prolonged network/authentication failures remain reviewable with hourly reconciliation. No automated refund or operator-resolution workflow exists.

Midtrans webhook verifies the exact SHA512(order_id + status_code + gross_amount + ServerKey) with timing-safe comparison, persists minimal deduplicated PaymentEvent metadata before acknowledgement, and schedules authenticated status retrieval. It never uses notification status alone as settlement proof. Match merchant, reference, transaction, integer amount, IDR, QRIS, and applicable fraud status. Settlement alone confirms payment. Transactionally update payment/order/reservation and unique notification intent; stale pending/expire cannot overwrite success. Before capacity release, verify terminal nonpayment; local deadlines only trigger reconciliation/cancellation. Cancellation is a request, not a guarantee. Late settlement after release or elapsed pickup preserves SUCCEEDED and marks the order REQUIRES_REVIEW.

Payment jobs use payment row leases; asynchronous messages use CheckoutNotification claims and leases. Stop the checkout worker before messaging teardown/database disconnect. Workers start only on listening. Scope payment claims by gateway/merchant and notification claims by original messaging provider/account. Recheck approved contacts at send time; respect the Cloud 24-hour window. QR instructions wait until the originating inbox response has left active processing. Persist sending before transport; interrupted/ambiguous sends become uncertain and never automatically replay. Only safe image-fetch failures or existing explicit Cloud text rate-limit rejection may retry automatically. Explicit Kirim Ulang QR resends the same payment instructions, never another charge. Keep one logical settlement confirmation per order; CEK can show status without creating another confirmation intent.

Image adapters accept validated PNG bytes/captions. Fetch gateway QR images only from exact trusted Midtrans origins and QR paths, HTTPS, no redirects/URL credentials/query, 2 MB maximum, valid PNG MIME/signature, five-second deadlines. Never send arbitrary customer URLs to adapters or log QR URLs/payloads. Mock sends a plain non-QR PNG with SIMULASI — TIDAK DAPAT DIBAYAR caption. Mock gateway state persists independently of local payment state; development-only payment:mock CLI simulates provider outcomes, never HTTP/customer commands. payment:inspect prints reference/status/amount/recovery data without customer routing IDs or credentials.

Extend the existing strict state data for SELECT_PICKUP, CONFIRM_CHECKOUT, AWAITING_PAYMENT, ORDER_CONFIRMED, PAYMENT_UNSUCCESSFUL, REQUIRES_REVIEW. READY remains unplaced until explicit Lanjut Checkout and final confirmation. Five-option pagination and stable fingerprints prevent stale numeric selections. Session inactivity does not cancel payment. CEK schedules coalesced reconciliation with a persistent 30-second cooldown. BATAL during unresolved checkout requests cancellation; Menu only browses. No manual customer payment-success command is permitted. Payment confirmation explicitly says tenant preparation is unconfirmed and never claims ready-for-pickup or tenant notification.

Tests use separate guarded _test PostgreSQL and suite-owned cleanup: notification/events/mock transaction/payment/reservation/items/order before frozen cart/session/customer/catalog. Do not truncate or delete development commerce history. Test final-slot races, snapshot immutability, duplicate engine confirmations, rollback before prepared response, ambiguous creation/restart, stale/late evidence, verified cancellation/release, image failure and uncertain send suppression, identity/tenant isolation, configuration privacy, and all prior regressions. Live Phase 6 Baileys and Midtrans Sandbox end-to-end behavior remains unverified until actual test-device exchanges and Sandbox provider transactions demonstrate it.

Midtrans customer-facing checkout copy uses normal QRIS wording without Sandbox/simulation banners; retain Sandbox identification in developer tooling/documentation and enforce Sandbox configuration. Use checkout/messages.ts for initial/resend instructions, help, friendly Indonesian payment status labels, and verified-payment confirmation. Mock retains its explicit SIMULASI — TIDAK DAPAT DIBAYAR label and non-QR placeholder; never substitute that image for a missing Midtrans QR. Do not rewrite already prepared conversation turns or historical notification text when changing copy. Actual Sandbox QR generation still requires configured private credentials; never silently switch providers or fall back to mock.

Unresolved checkout must permit read-only tenant/category/menu navigation, including numeric selections and back commands. Block additions/cart mutations/new checkout while preserving browsing context. Before CEK/BATAL/QR resend schedules work, match the persisted payment provider and merchant against the configured gateway; mismatches are read-only and explain unavailable processing without promising cancellation. Render status using the stored payment provider, never relabel old mock payments as Midtrans. Overdue unverified and cancellation-pending payments must not show or enqueue QR resend. Do not infer cancellation/expiry from local timestamps or configuration changes, migrate payments automatically, or release holds without verified evidence.
